inline-email turns HTML and CSS into email-safe templates you compile once and render per send. It is built to be simple and durable, to work across many email clients, and to make emails clear and easy. It is for teams that treat email as a necessary part of their product, worry about dependency bloat, and do not want to build on juice from scratch.

**Docs:** [Transactional email](docs/guides/transactional.md) · [CLI preview](docs/guides/cli-preview.md) · [Marketing email](docs/guides/marketing.md) · [Data-heavy digest](docs/guides/digest.md) · [Reference](docs/reference.md) · [Migrating from 3.x](MIGRATION.md)

> **Upgrading from 3.x?** inline-email 4.0 renders templates with Handlebars. Most 3.x templates work unchanged; [MIGRATION.md](MIGRATION.md) lists every difference with before-and-after examples and ends with a prompt you can paste into an AI assistant, together with your templates, to convert them.

Migrating from the v2 package? Start with the [v3 migration guide](https://github.com/freethinkingit/inline-email/wiki/Migrating-to-v3).

## When to use it

- Use inline-email when you want server-side templates, compiled once and rendered per send, written in plain HTML and CSS with few dependencies.
- Use [MJML](https://mjml.io/) when you want a full email markup language with its own component set and are happy with its toolchain.
- Use [React Email](https://react.email/) when your templates are React components and your stack already renders React on the server.
- Use [juice](https://github.com/Automattic/juice) on its own when you only need CSS inlining and already have templating.

## Quickstart

Install the package:

```sh
npm install inline-email
```

Save the two files below in one folder as `welcome.html` and `send.mjs`.

Write a template with a variable, a block and a slot:

```html file=examples/guides/quickstart/welcome.html
<email>
  <preview>Welcome to ACME, {{firstName}}.</preview>
  <container>
    <section padding="32">
      <h1 class="headline">Hi {{firstName}}, welcome to ACME.</h1>
      {{slot:summary}}
      <p>Three things to try first:</p>
      <ul>
        {{#items}}
        <li>{{this}}</li>
        {{/items}}
      </ul>
      <spacer size="24" />
      <button href="{{appUrl}}">Open ACME</button>
    </section>
    <footer>Sent by ACME</footer>
  </container>
</email>
```

Compile it once and render it per send:

```js file=examples/guides/quickstart/send.mjs
import { readFileSync } from 'node:fs';
import { compileEmailTemplate } from 'inline-email';

const html = readFileSync(new URL('./welcome.html', import.meta.url), 'utf8');
const css = '.headline { font-size: 24px; color: #111827; }';

const compiled = await compileEmailTemplate({
  subject: 'Welcome to ACME, {{firstName}}',
  html,
  css,
  text: 'Hi {{firstName}}, welcome to ACME. Open it at {{appUrl}}.'
});

const email = compiled.render({
  data: {
    firstName: 'Dan',
    appUrl: 'https://app.acme.example',
    items: ['Create a project', 'Invite a teammate', 'Connect your calendar'],
    slots: {
      summary: '<p>Your account is ready.</p>'
    }
  }
});

console.log(JSON.stringify(email, null, 2));
```

Run `node send.mjs`. It prints the rendered email, trimmed here to the meaningful lines:

```text
{
  "subject": "Welcome to ACME, Dan",
  "html": "<!doctype html>\n<html>\n<head>\n ... <h1 class=\"headline\" style=\"font-size: 24px; color: #111827;\">Hi Dan, welcome to ACME.</h1>\n      <p>Your account is ready.</p>\n ... <li>Create a project</li>\n ... </html>\n",
  "text": "Hi Dan, welcome to ACME. Open it at https://app.acme.example."
}
```

## Status

The package targets Node.js 22, 24, and 26.

## Quality

- [CI workflow](https://github.com/freethinkingit/inline-email/actions/workflows/ci.yml) runs install, high-severity audit, lint, build, tests, examples, and an install-and-run check of the packed package on Node.js 22, 24, and 26.
- The linter is ESLint, configured in [`eslint.config.js`](eslint.config.js); it must report nothing.
- The coverage gate fails `npm test` when line or branch coverage of `src/` drops below 99%.
- Tests live in [`test/`](test/), and visual regression tests compare rendered emails against approved screenshots.

When an intentional layout change updates the screenshots:

```sh
npm run test:visual -- --update-snapshots
```

## Development

```sh
npm ci
npm run check
npx playwright install chromium
npm run test:visual
```

`npm run check` runs lint, build, tests with the coverage gate, and examples, all offline. CI also runs `npm run audit`, `npm run test:package` and the visual tests. The visual tests need the browser installed once, and their approved screenshots exist only for macOS. [CONTRIBUTING.md](CONTRIBUTING.md) covers setup, coverage per module, branch naming and issues.

## Release

A release is a version tag that matches `package.json`; GitHub Actions publishes it to npm with provenance and creates a GitHub Release. The steps, from the version bump to the tag, are in [CONTRIBUTING.md](CONTRIBUTING.md#releases).

```sh
git tag v<x.y.z> origin/master
git push origin v<x.y.z>
```

## What This Does Not Do

`inline-email` does not validate that your markup uses only email-safe HTML tags, and it does not replace unsafe tags for you.
